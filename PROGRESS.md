## Recent Features (2025-11-10)

### NEW in Version 0.3.0 ✅

**Alert Cooldown & Recovery Check (Spam Prevention)**

Implemented flexible alert throttling to prevent alert fatigue from persistent anomalies:

**Problem Solved:**
- 10min interval metric with real 5-hour anomaly = 30 duplicate alerts
- No way to control alert frequency for long-running issues
- Alert spam makes important alerts invisible

**Solution: Hybrid Cooldown System**

1. **Configurable Cooldown Period**
   - `alert_cooldown: "30min"` - minimum interval between alerts
   - Supports string ("30min", "1h") or int (1800 seconds)
   - If not set → no cooldown (alerts every time)

2. **Optional Recovery Reset**
   - `cooldown_reset_on_recovery: true` - reset timer when metric recovers
   - Recovery = consecutive anomalies drop below threshold
   - Allows immediate alert if new anomaly after recovery

**Configuration Example:**
```yaml
alerting:
  consecutive_anomalies: 3
  alert_cooldown: "30min"           # Minimum 30min between alerts
  cooldown_reset_on_recovery: true  # Reset on recovery (default)
  channels:
    - mattermost_analytics
```

**Implementation Details:**

1. **Database Schema (_dtk_tasks table)**
   - Added `last_alert_sent` (Nullable DateTime64) - tracks last alert timestamp
   - Added `alert_count` (UInt32) - counts total alerts sent

2. **AlertConfig Model**
   - `alert_cooldown: Optional[Union[str, int]]` - cooldown interval
   - `cooldown_reset_on_recovery: bool = True` - recovery behavior

3. **InternalTablesManager Methods**
   - `get_last_alert_timestamp(metric_name)` - retrieve last alert time
   - `update_alert_timestamp(metric_name, timestamp, increment_count)` - update after sending

4. **AlertOrchestrator Logic**
   - `_is_in_cooldown()` - check if currently in cooldown period
   - `_check_recovery_since_last_alert()` - detect metric recovery
   - Integrated into `should_alert()` - checks cooldown BEFORE expensive checks
   - Integrated into `send_alerts()` - updates timestamp after successful send

**Behavior Examples:**

**Scenario 1: Strict Cooldown (cooldown_reset_on_recovery=false)**
```
10:00 - Anomaly detected → Alert sent ✓
10:10 - Anomaly persists → Cooldown active, skip
10:15 - Recovery to normal
10:20 - NEW anomaly → Cooldown still active (20min < 30min), skip
10:30 - NEW anomaly → Cooldown expired → Alert sent ✓
```

**Scenario 2: Recovery Reset (cooldown_reset_on_recovery=true)**
```
10:00 - Anomaly detected → Alert sent ✓
10:10 - Anomaly persists → Cooldown active, skip
10:15 - Recovery to normal → Cooldown RESET
10:20 - NEW anomaly → Alert sent ✓ (recovery reset cooldown)
```

### 2. ⚠️ NOT RECOMMENDED: Vectorize MAD Detector
**Status:** EVALUATED - NOT WORTH IT

**Current Performance (measured 2025-11-07):**
- 36,242 points processed in 25 seconds (including I/O)
- **~1,450 points/sec** - acceptable for production use
- Total time includes: ClickHouse I/O + detection + saving results

**Why NOT vectorizing:**
- ✅ Current performance is acceptable
- ✅ Code is readable and maintainable
- ❌ Seasonality grouping makes vectorization VERY complex
- ❌ Each point needs unique seasonality mask
- ❌ Group sizes vary dynamically (10-20 points per group)
- ❌ Real speedup would be only 3-5x (I/O dominates)
- ❌ High risk of introducing bugs

**Possible approaches (if needed in future):**
1. Use `numba` JIT compilation - 5-10x speedup without logic changes
2. Full vectorization - requires complete rewrite with complex index operations

**Recommendation:** Keep current implementation unless performance becomes a bottleneck

## Key Design Decisions

1. **Universal Database Manager** - Generic methods work with ANY table
2. **Intervals** - Custom parser (no pandas dependency)
3. **Seasonality** - JSON storage for flexibility
4. **Duplicates** - ReplacingMergeTree + PRIMARY KEY strategy
5. **Idempotency** - Check last timestamp from data tables (not tasks)
6. **Detectors** - Hash = class name + sorted non-default params
7. **Timezone** - All datetime normalized to naive (UTC assumed)
8. **Batching** - Both load and detect use configurable batch sizes
