# detectkit - Библиотека для мониторинга метрик

## Общее описание

Библиотека на Python для аналитиков и дата-инженеров, предназначенная для мониторинга метрик с автоматическим обнаружением аномалий.

**Название:** detectkit  
**Язык:** Python  
**Основной принцип:** работа через numpy-массивы (без pandas в ядре логики)

---

## Архитектура данных

### Входные данные от аналитика

Аналитик предоставляет SQL-запрос к БД (например, ClickHouse), который возвращает:
- **Временная колонка** - интервалы времени (10 мин, час и т.д. - настраиваемо)
- **Колонка метрики** - значения метрики
- **Сезонные колонки** (опционально) - дополнительные колонки для учета сезонности

Аналитик указывает маппинг колонок (где время, где метрика, где сезонные данные).

### Внутреннее хранилище

Две технические таблицы с типизированными колонками:

1. **Таблица данных метрики** - сохраненные исторические данные
2. **Таблица результатов детекции** - результаты работы детекторов (аномалии, доверительные интервалы, метаданные)

**Уникальный ключ для детектора:** хэш из названия детектора + отсортированных не-дефолтных параметров

Названия таблиц - по дефолту будут - `_dtk_datapoints` и `_dtk_detections`. При этом хотелось бы иметь возможность для разных метрик разные таблицы использовать - обсудить как это делать лучше (мб через профили как то или в отдельном конфиге всего проекта?)
ВАЖНО: у нас будут менеджеры баз данных - и у них будут универсальные методы работы с разными таблицами - чтобы менеджеры могли работать с нашими таблицами, у нас отдельно должны быть их модели или датаклассы.
ВАЖНО: для разных бд мы можем в разных схемах или database (как в кликхаусе) хранить эти таблицы. Мы должны этим управлять из profiles. Пример - я хочу чтобы у меня эти таблицы в кликхаусе хранились в `marts` - тогда они будут доступны из `marts._dtk_...`. ЕЩЕ - в некоторых базах данных есть схемы, а вот в кликхаусе их нет и вместо них database. Надо это учесть как то универсально. 
Подразумевается, что у нас будут общие таблицы для разных метрик и результатов детекций по дефолту, но можно будет с этим гибко работать - для разных метрик разные таблицы (это предусматриваем для расширения) - либо для каждой метрики своя таблица либо группировать метрики по разным таблицам - это должно быть настраиваемо каким то образом! Но даже если будем писать каждую метрику в свою таблицу - мы всеравно должны в таблицу передавать название метрики (т.к. у нас будут универсальные методы работы с таблицами и названия метрик будут браться оттуда а не из названия таблицы!)

### Хранение сезонных колонок

Проблема: разные метрики имеют разные сезонные колонки, но нужно типизированное хранилище.  
Решение: будем хранить в виде JSON и быстро парсить их когда достаем.

## Процесс: Загрузка и сохранение данных метрики

### Основной процесс

Аналитик указывает в конфиге метрики:
- **С какого времени загружать данные** (start_load)
- **С какого времени детектить** (start_detect) - может отличаться, т.к. нужно историческое окно

Запрос содержит переменные (согласованные заранее) для извлечения любого периода. Данные загружаются **батчами** (размер настраивается аналитиком) и сохраняются в типизированную внутреннюю таблицу.

### Идемпотентность

- Определяется последняя временная точка в хранилище
- При перезапуске загрузка продолжается с места остановки
- Позволяет прерывать и возобновлять процесс без дублирования

### Обработка пропущенных данных

Если во входных данных отсутствуют точки (например, есть 12:10, 12:30, но нет 12:20):
- Сохраняются как `None`/`NaN`
- **Требование:** все детекторы должны корректно работать с пропущенными данными

## Процесс: Детекция аномалий

### Детекторы

**Типы детекторов:**
- Статистические детекторы
- Простой детектор с ручным указанием доверительного интервала 
- Детекторы должны уметь работать с сезонностью (все кроме простого с ручными границами)
- Так же мы будем в будущем добавлять детекторы, работающие на других библиотеках - prophet, timesfm (от гугл) и т.д. и т.к. это будут тяжелые зависимости, мы должны учесть, что установка таких детекторов будет через опциональные зависимости через extras так же как и для работы с разными базами данных. ВНИМАНИЕ ВАЖНО - у нас будут отдельные extras для бд и отдельно для детекторов некоторых - как это грамотно учесть?

**Работа с сезонностью:**
- Каждая сезонная колонка как отдельная компонента
- Комбинации колонок как одна компонента
- Гибкие вариации (например: 2 колонки объединены + 1 отдельная = 2 компоненты)

Сложный кейс:
  Аналитик хочет следующую комбинацию сезонности:
  - Компонента 1: day_of_week + hour
  - Компонента 2: is_holiday
  - Компонента 3: month
  Как это будет описываться в конфиге метрики?
  Вопрос: Детектор должен получать numpy массив для каждой компоненты отдельно? Или это решает сам детектор как использовать?
  В конфиге метрики мы будем просто указывать равноценно все сезонные колонки. А уже в конфиге детектора в конфиге метрики мы будем указывать комбинации сезонных колонок!

У нас должен быть какой то один парсер сезонных колонок (т.к. они будут в JSON храниться) и он должен быть максимально эффективным - через него будем доставать все сезонные колонки в детекторе в виде массивов и уже детектор будет сам понимать как ими оперировать исходя из собственного конфига.

### Историческое окно

Для каждой точки детектор использует историческое окно (настраивается аналитиком).

**Пример:** анализ точки 29 апреля 13:00 с окном 1 месяц:
- Детектор получает данные за месяц до 13:00 + текущую точку
- Рассчитывает доверительный интервал
- Определяет, является ли точка аномалией

### Батчевая обработка

Детекторы работают **с периодами, а не с отдельными точками** (и загрузка данных метрики ДО работы детекторов тоже):

**Причины:**
- Эффективность: не нужно для каждой точки отдельно загружать историческое окно
- Оптимизация: данные загружаются массивами, расчет идет через смещение
- Универсальность: прод-режим (одна последняя точка) - частный случай периода

**Процесс:**
- Аналитик настраивает размер батча (отдельно мы можем указывать в конфиге батч для загрузки данных метрики и отдельно для детекторов)
- Если для детектора период: 1-10 марта, окно: 30 дней → загружается с 1 февраля по 10 марта данные для работы детектора
- Результаты для каждой точки: доверительный интервал, флаг аномалии, метаданные детектора

### Формат данных

- Расчеты через **numpy**
- Хранение/передача: датакласс с numpy-массивами
- Pandas только для вспомогательных методов вывода результатов

### Идемпотентность детекции

- Определяется, за какое время уже записаны результаты детекции
- При перезапуске процесс продолжается с последней обработанной точки

## Процесс: Алертинг

### Архитектура алертинга

```
detectkit/
  ├── alerting/
  │   ├── channels/           # Каналы отправки
  │   │   ├── base.py        # Абстрактный channel
  │   │   ├── mattermost.py  # Приоритет
  │   │   ├── slack.py
  │   │   ├── telegram.py
  │   │   └── email.py
  │   ├── decision.py         # AlertDecisionEngine
  │   └── orchestrator.py     # AlertOrchestrator
```

### AlertDecisionEngine

Логика принятия решения об отправке алерта:
- Проверяет наличие аномалии в последней точке
- Определяет направление аномалии (вверх/вниз)
- Проверяет соответствие настройкам (направление, N аномалий подряд)
- Возвращает решение: отправлять алерт или нет

**Настройки:**
- Алерт при аномалии: вниз / вверх / любое направление
- Алерт только при N аномалий подряд и их направление (вверх,вниз,в одну сторону, в любые стороны) (опционально)

### AlertChannel

Базовый класс и реализации для каналов:
- `send(message, destination)` - отправка сообщения
- **Приоритет:** Mattermost (через webhook)
- Так же реализуем slack, email, telegram

### AlertOrchestrator

Координация процесса алертинга:
- Определяет последнюю полную временную точку относительно now (UTC)
  - Пример: сейчас 13:23, интервал 10 мин → точка 13:10
- Вызывает AlertDecisionEngine
- При положительном решении → вызывает AlertChannel
- В случае если данных нет, то по дефолту нужен отдельный алерт об этом (но это поведение можно будет отключать из конфига метрики) НО обычно перед тем как запустить алерт будет отрабатывать сохранение данных метрики и детектинг - и вот в случае если после этого данных по точке нет этой - то будем вызывать отдельный алерт. 
- Последняя точка будет браться по UTC времени и в бд ОБЯЗАТЕЛЬНО должно быть UTC время. Аналитики обязаны писать запрос, который будет возвращать время в колонке по UTC

### Шаблоны алертов

- Стандартное сообщение по умолчанию
- Аналитики могут добавлять кастомные шаблоны
- Возможность включения дополнительных данных

### Управление алертингом

**По умолчанию:** запускается весь пайплайн (загрузка → детекция → алертинг)

**Отключение алертинга:**
- Через переменную в конфиге
- Через CLI: `dtk run --some-command` (без изменения конфига)

**Алерт об отсутствии данных:**
- Если данных нет для последнего периода → отправка алерта (но отдельного со своим шаблоном)
- Поведение настраивается в конфиге (можно отключить)

Причем не будем хардкодить работу с внутренними таблицами в этот класс. Этот будет менеджер баз данных для работы с нашей библиотекой - он может создавать таблицы, выгружать данные в нужном нам формате, проверять создана ли таблица и т.д. и т.п.

## Батчи и историческое окно
Вопрос по оптимизации:
Если детектируем период 1-10 марта с окном 30 дней:
- Загружаем данные с 1 февраля по 10 марта
- Для точки 1 марта используем окно [1 фев - 1 март]
- Для точки 2 марта используем окно [2 фев - 2 март]
- ...
Это значит, что детектор должен получить ВЕСЬ массив данных и сам управлять смещением окна? Или мы подготавливаем для каждой точки отдельный массив?
Ответ - детектор должен сам управлять смещением окна - он принимаем весь массив и при этом мы будем знать до какой точки у нас уже продетектированы данные - мы будем понимать с какой точки надо детектить.

## Пропущенные данные
Детекторы будут игнорировать пропущенные данные - но отдельно в detection_metadata - хорошо бы писать процент пропущенных данных в окне для каждой точки (типа если для точки в окне 30% данных было пропущено то запишем 0.3).

## Хэш детектора

Вопрос по генерации хэша:
Детектор с параметрами:
detector:
name: statistical_zscore
params:
    threshold: 3.0
    window_days: 30
    min_samples: 100  # default = 100

Хэш = hash("statistical_zscore" + sorted([("threshold", 3.0), ("window_days", 30)]))
То есть min_samples не включается, т.к. это дефолтное значение!
Проблема: Если позже аналитик изменил параметр с дефолтного на другой, хэш изменится → создастся новый детектор → старые результаты останутся в таблице - это окей! ведь технически будем считать что это уже новый детектор!

## Алертинг и временные зоны

Сложный кейс:
- Данные в БД в UTC (обязательно)
- Аналитик в МСК (UTC+3)
- Сейчас 13:23 MSK = 10:23 UTC
- Интервал метрики: 10 минут
- Последняя полная точка: 10:10 UTC = 13:10 MSK
Вопросы:
- В алерте показывать время в UTC или в локальной timezone аналитика?
- Как аналитик укажет свою timezone? В конфиге метрики или в профиле?
Ответ: в конфиге метрики в конфиге алертера можно будет указать часовой пояс алерта и в алерте будет указано время соответствующего часового пояса. Часовые пояса должны указываться в конфиге так чтобы не делать дополнительного маппера по поясам (наверняка оно уже встроено в datetime библиотеку)

class BaseDatabaseManager(ABC):
    @abstractmethod
    def execute_query(self, query: str, params: dict) -> np.ndarray:
        """Выполнить запрос и вернуть результат как numpy массив"""

    @abstractmethod
    def create_table(self, table_model: TableModel):
        """Создать таблицу по модели"""

    @abstractmethod
    def table_exists(self, table_name: str, schema: str) -> bool:

    @abstractmethod
    def insert_batch(self, table_name: str, data: np.ndarray, columns: List[str]):
        """Вставить батч данных"""

    @abstractmethod
    def get_last_timestamp(self, table_name: str, timestamp_column: str) -> Optional[datetime]:
        """Получить последнюю временную точку"""

## Структура конфига метрики

Можешь показать примерный полный конфиг метрики? Хочу понять:
- Как указывается SQL-запрос с переменными для периода?
- Как маппятся колонки?
- Как настраивается каждый детектор?
- Как настраивается алертинг?

Пример конфига:
```
  metric:
    name: "orders_count_10min"
    profile: "clickhouse_prod"

    tags: ["10min", "orders", "critical"]

    query: |
      SELECT 
        toStartOfTenMinutes(created_at) as time_interval,
        count(*) as metric_value,
        toDayOfWeek(time_interval) as day_of_week,
        toHour(time_interval) as hour,
        league_day
      FROM orders
      WHERE created_at >= {start_time} AND created_at < {end_time}
      GROUP BY time_interval, day_of_week, hour
      ORDER BY time_interval

    query_columns:
      timestamp: "time_interval"
      metric: "metric_value"
      seasonality: ["day_of_week", "league_day", "hour"]

    interval: "10min"
    loading_start_time: "2024-01-01 00:00:00"  # UTC
    loading_batch_size: 1000  # количество точек в батче

    detectors:
      - name: "some_detector"
        params:
          threshold: 3.0
          window_size: 10 * 6 * 24 * 30 # чтобы получить 30 дней чз 10интервальные отрезки
          start_time: "2024-02-01 00:00:00"  # после накопления истории
          batch_size: 500
          seasonality_components: # если компоненты комбинируются то перечисляем списком
            - "day_of_week"
            - ["league_day", "hour"]

    alerting:
      enabled: true
      timezone: "Europe/Moscow"

      channels:
        - type: mattermost
          webhook_url: "${MATTERMOST_WEBHOOK}"  # из env переменной

      conditions:
        direction: "same"  # "same" / "any" / "up" / "down"
        consecutive_anomalies: 2  # опционально (по умолчанию = 1)

      no_data_alert: true

      template: | # опционально, будет дефолтный алерт без эмодзи
        🚨 Anomaly detected in metric: {metric_name}
        Time: {timestamp} ({timezone})
        Value: {value}
        Confidence interval: [{lower}, {upper}]
        Detector: {detector_name}
```
Нюансы - мы хотим иметь возможность указывать в конфиге запрос ИЛИ же сослаться на запрос какойто у нас в проекте. Для этого при инициализации проекта у нас будет создаваться помимо папки /metrics в проекте - дефолтная папка /sql (это в конфиге проекта будет прописано, можно будет поменять папку) - и в этой папке можно будет хранить запросы в разных вложеннных папках. В таком случае в конфиге можно будет указать путь к sql файлу относительно этой папки - например если у нас есть файл /{project_name}/sql/some_query.sql то пользователю можно будет указать some_query.sql а если файл будет в /{project_name}/sql/some_folder/some_query.sql - то юзер укажет some_folder/some_query.sql.
Еще - т.к. мы задаем интервалы все числами по числу точек - при этом реально доставать из бд окна и периоды мы должны по реальным таймстампам - ведь может быть такое что части точек нет в выгрузке из первоначального запроса - это не должно влиять на размер окна (т.е. если 10 точек указано и интервал 1 день то мы должны брать реально 10 дней снизу даже если пары точек нету - период не должен расшириться.)

## Дополнительные сложные сценарии для обсуждения

  Сценарий 1: Изменение параметров детектора

  Аналитик изменил threshold с 3.0 на 2.5. Что происходит?
  - Хэш меняется
  - Старые результаты остаются в таблице (с другим хэшем)
  - Начинается детекция заново с start_time?
  Ответ: да начинается детекция заного.

  Сценарий 2: Ретроспективная детекция

  Аналитик хочет переDetectить исторические данные (например, нашел ошибку в SQL):
  - Как это делать? Удалить старые результаты и запустить заново?
  - CLI команда типа dtk run --somecommand detect --select... --from 2024-01-01?
  Ответ: да, сделаем так - если указан --from то удаляем все данные начиная с него (из таблицы детекций) и запускаем прогрузку заного. В случае если не хотим указывать даты и передетектить то вместо --from укажем --full-refresh - тогда удалим все данные и перезапишем. Эта же логика будет работать и для детектора и для load процесса - таким же образом.

  Сценарий 3: Несколько детекторов и алертинг

  У метрики 3 детектора. Алерт отправляется если:
  - Хотя бы один детектор нашел аномалию?
  - Все детекторы нашли аномалию?
  - Настраивается аналитиком?
  Ответ: Давай по дефолту - если хотя бы 1 детектор нашел аномалию (или число аномалий подряд). Заведем параметр - число детекторов - если число больше 1 то тогда будем смотреть чтобы условие соблюдалось для указанного числа детекторов. Но как тогда быть с шаблоном алерта - не писать же два или более доверительных интервалов для каждого из детекторов в таком случае ? Тогда в таком случае будем использовать другой шаблон без доверительных интервалов где будет указываться какие детекторы сработали - вообщем как то оптимально чтобы не слишком большой алерт был.

  Сценарий 4: Метрика с очень редким интервалом

  Метрика с интервалом 1 день. Историческое окно 365 дней.
  - Батч для детекции = 30 точек = 30 дней данных для детекции
  - Загружаем данные за 30 + 365 = 395 дней
  - Это нормально или нужна оптимизация?
  Ответ: Если мы так захотим то это нормально - 365 строк выгрузить из промежуточной таблицы будет несложно (для того мы и делаем внутреннюю таблицу для хранения данных самой метрики - чтобы в случае если запрос тяжелый у нас не было проблем)

  - Не можем перезапустить пока не пройдет N минут

  Ответ: добавить timeout в конфиг метрики:
  ```
  metric:
    name: "orders_count_10min"

    timeouts:
      load: 900     # 15 минут (в секундах)
      detect: 600        # 10 минут
      alert: 60          # 1 минута
  ```

  CLI флаг для принудительного перезапуска:
  dtk run --select config.yml --force
  При --force:
  - Игнорируем проверку running статуса
  - Обновляем статус на running для текущего процесса
  - Продолжаем с last_processed_timestamp

  Схема _dtk_tasks:
  CREATE TABLE _dtk_tasks (
    metric_name String,
    detector_id String,        -- пустая строка для load процесса
    process_type String,       -- 'load' / 'detect' / 'alert'
    status String,             -- 'running' / 'completed' / 'failed'
    started_at DateTime64(3, 'UTC'),
    updated_at DateTime64(3, 'UTC'),
    last_processed_timestamp Nullable(DateTime64(3, 'UTC')),
    error_message Nullable(String),
    timeout_seconds Int32,
    PRIMARY KEY (metric_name, detector_id, process_type)
  )

  Логика при запуске:
  ```
  def can_start_process(metric_name, detector_id, process_type, force=False):
      task = get_task(metric_name, detector_id, process_type)

      if not task:
          # Первый запуск → создаем задачу
          return True

      if force:
          # Принудительный запуск
          return True

      if task.status == 'running':
          elapsed = now() - task.started_at
          if elapsed > task.timeout_seconds:
              # Зависший процесс → можно перезапустить
              return True
          else:
              # Еще работает
              return False

      if task.status in ['completed', 'failed']:
          # Можно запустить (продолжим с last_processed_timestamp)
          return True
  ```

  - Батч: 1000 точек = ~7 дней данных

  - Будет выполнено 9 запросов к БД

  1. Загрузка батча 1: 2024-01-01 00:00 → 2024-01-08 06:40 (1000 точек)
  2. Сохранение в _dtk_datapoints
  3. Обновление _dtk_tasks.last_processed_timestamp = 2024-01-08 06:40
  4. Загрузка батча 2: 2024-01-08 06:50 → ...
  5. ...

  Кстати еще - нам нужен будет какой то компонент, проверяющий эффективно на наличие дублей все бетчи, с которыми взаимодействует библиотека (и бетчи данных метрики и детекций - там где это критично, вдруг аналитик запрос криво написал и временные точки дублятся и тогда на всех след.этапах будут проблемы)!

Базовые статистические детекторы (которые будут встроены по умолчанию в библиотеку)

Детектор работает с сезонностью через **мультипликативные корректировки** базовых статистик (центральной тенденции и разброса).

**Важно**: Вся работа идет **только через numpy массивы** - никакого pandas, максимальная производительность.

Примерный алгоритм:

1. **Вычисляем веса для исторического окна** (опционально):
   - Экспоненциальные веса: более свежие точки важнее старых
   - Линейные веса: постепенное увеличение важности к текущей точке
   - Без весов: все точки равнозначны
   - Веса нормализуются (сумма = 1)

2. **Вычисляем глобальные взвешенные статистики** для всего исторического окна:
   - `global_center` (взвешенная медиана, среднее или другая мера центра)
   - `global_spread` (взвешенный MAD, стандартное отклонение или другая мера разброса)

3. **Для каждой сезонной компоненты/группы компонент**:
   - Создаем булевую маску через numpy для фильтрации данных окна по значениям этой компоненты/комбинации
   - Применяем маску к данным И весам
   - Вычисляем взвешенные `component_center` и `component_spread` для отфильтрованных данных
   - Получаем мультипликаторы: 
     - `center_multiplier = component_center / global_center`
     - `spread_multiplier = component_spread / global_spread`

4. **Применяем корректировки к базовым статистикам**:
   - Перемножаем все мультипликаторы от всех компонент/групп
   - `adjusted_center = base_center × Π(center_multipliers)`
   - `adjusted_spread = base_spread × Π(spread_multipliers)`

5. **Строим доверительный интервал** из скорректированных статистик:
   - `lower = adjusted_center - threshold × adjusted_spread`
   - `upper = adjusted_center + threshold × adjusted_spread`

Примеры для разных детекторов:
- **MAD-детектор**: center=взвешенная медиана, spread=взвешенный MAD
- **Z-score детектор**: center=взвешенное среднее, spread=взвешенный std
- **Percentile детектор**: center=взвешенная медиана, spread=взвешенный IQR

Конфигурация групп сезонности:
Детектор принимает конфиг с гибкой группировкой сезонных компонент:
- Пример: `[["day_of_week", "hour"], ["is_holiday"]]` = 2 группы
- Для каждой группы вычисляется свой мультипликатор

Итог для реализации:
Детектор должен:
1. Вычислять веса для окна (если включено взвешивание)
2. Принимать конфиг с группировкой сезонных компонент
3. Для каждой группы создавать numpy boolean маски для фильтрации данных окна по комбинации значений компонент
4. Применять маски к данным И весам, пересчитывать веса для отфильтрованных данных
5. Вычислять взвешенные мультипликаторы для каждой группы через numpy операции
6. Перемножать мультипликаторы всех групп для финальной корректировки

**Все операции только через numpy - без pandas, циклов по точкам где возможно, максимальная векторизация.**

Детектор: передача данных

У нас будет один датакласс на данные метрики (до детекций) и на данные детекций. Мы не будем создавать отдельные датаклассы на input, output и т.д. чтобы не усложнять структуру. Детекторы на вход получают данные метрики и отдают данные детекций, а алертер получает данные детекций. Для разных нужд где это необходимо у нас просто будут конвертеры, которые будут превращать данные в эти датаклассы или из них в нужный формат. Тоесть мы НЕ будем делать отдельный датакласс для ОДНОЙ точки данных метрики или детекций!
По поводу взаимодействия компонентов системы друг с другом и с бд - мы НЕ используем пандас датафреймы - даже для записи в базу данных или выгрузки из бд!!! С ними кажется проще, НО пандас не эффективен и может быть куча проблем со стабильностью в разных его версиях!!

Базовый интерфейс детектора:

from abc import ABC, abstractmethod

class BaseDetector(ABC):
    def __init__(self, **params):
        self.params = params
        self._validate_params()

    @abstractmethod
    def _validate_params(self):
        """Валидация параметров детектора"""
        pass

    @abstractmethod
    def detect(self, data: DetectionInput) -> DetectorOutput:
        """
        Основной метод детекции.
        Детектор должен:
        1. Обработать данные начиная с data.detection_start_idx
        2. Для каждой точки использовать историческое окно
        3. Вернуть результаты для всех точек начиная с detection_start_idx
        """
        pass

    def get_hash(self) -> str:
        """Генерация хэша детектора"""
        non_default_params = self._get_non_default_params()
        sorted_params = sorted(non_default_params.items())
        hash_string = self.__class__.__name__ + str(sorted_params)
        return hashlib.sha256(hash_string.encode()).hexdigest()[:16]

    @abstractmethod
    def _get_non_default_params(self) -> Dict:
        """Возвращает параметры, отличающиеся от дефолтных"""
        pass

Парсинг JSON для сезонности

Требование: Максимально эффективный парсинг JSON → numpy массивы
Принцип работы:
1. **Используем orjson** вместо стандартного json (в 4-5 раз быстрее)
2. **Pre-allocation numpy массивов**:
   - Парсим первую JSON строку чтобы узнать ключи и их типы
   - Сразу создаем numpy массивы нужного размера (количество строк в батче)
   - Заполняем их значениями по индексу вместо append к спискам
3. **Обработка пропущенных данных**:
   - Если JSON строка None или пустая → записываем np.nan в соответствующие индексы всех массивов
4. **Минимум копирований**:
   - Списки требуют реаллокации при росте
   - Pre-allocated numpy массивы заполняются сразу по индексу без копирований
Это **максимально эффективное** решение для данной задачи.

Управление интервалами метрик

**Решение: Custom parser (без pandas)**

**Два формата в конфиге:**
```yaml
interval: 600        # число = секунды
interval: "10min"    # строка = простой формат
```

**Поддерживаемые строковые форматы:**
- Секунды: "30S" или "30s"
- Минуты: "10min" или "10m"
- Часы: "1H" или "1h"
- Дни: "1D" или "1d"

**Класс IntervalManager:**
- Принимает `Union[int, str]`
- Если `int` → секунды напрямую
- Если `str` → парсим через regex `(\d+)(S|s|min|m|H|h|D|d)` и словарь маппинга единиц в секунды
- Кэширует: секунды (int), timedelta, строковое представление
- Без внешних зависимостей (только stdlib: re, datetime)

**Методы:**
- `seconds` - для БД (Int32)
- `timedelta` - для вычислений
- `points_to_timedelta()`, `timedelta_to_points()` - конвертация точек ↔ время
- `floor_timestamp()` - округление через epoch и целочисленное деление
- `get_last_complete_point(now)` - последняя полная точка для алертинга
- `from_seconds(seconds)` - создание из БД с красивым форматированием (86400→"1D", 3600→"1H", 60→"1min", иначе→"XS")

**Обоснование:** Легковесно, покрывает все нужные кейсы, нулевые зависимости.

Если загрузили 5 батчей из 10, на 6-м ошибка:
- Статус failed, но в _dtk_datapoints уже есть 5 батчей
- При перезапуске продолжим с 6-го батча (идемпотентность) (точнее с )

3. Уведомления об ошибках:
Отправлять алерт если процесс failed? Нет, не отправлять. Отправляем отдельно только если данных в актуальной точке для алерта нет и это у нас отдельной переменной в конфиге управляется.

---
Производительность: Batch size vs Memory

Конфиг:
loading_batch_size: 10000  # 10K точек

Если интервал 10 минут:
- 10K точек = ~70 дней данных
- С сезонностью (3 колонки) + метрика + timestamp = 5 значений × 10K = 50K значений
- 50K × 8 байт (float64) = 400 KB в памяти

Для 100 метрик параллельно (если --threads 100):
- 40 MB в памяти

Вопросы:

1. Ограничение batch size:
Нужно ли валидировать максимальный размер? нет, мы же будем управлять параметрами параллелизации - если упало то наша проблема, да и вообще по дефолту у нас последовательное выполнение а параллельное уже дополнительно мы просто на будущее закладываем что появится.

2. Автоматическая подстройка:
Если аналитик указал batch_size: 1000000 (1M точек):
- ошибка с требованием уменьшить - давай определеимся какое окно (по числу точек) будет оптимально максимальное для рахных бд и такой лимит и захардкодим

3. Память для детекторов:
Детектор загружает батч 100 точек + окно 30 дней (4320 точек для 10min интервала):
- Всего 4420 точек в памяти

Для 100 метрик параллельно:
- 4420 × 100 × 5 значений × 8 байт = 17 MB

Критично ли это? Думаю нет, но стоит упомянуть в доке.
